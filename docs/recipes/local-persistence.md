# Local persistence recipe (Section 21.2)

**Classification:** Recipe only — **not** a schema-1 catalog profile.  
**Requirements:** REQ-075 (SPEC-FOUNDRY-002); companion exclusion REQ-073.  
**Normative anchor:** Section 21.2 of
[`docs/02-definitive-foundry-specification-revised-fable-5.md`](../02-definitive-foundry-specification-revised-fable-5.md).

This document is **post-generation guidance** for project owners and agents.
Foundry does **not** generate persistence packages, generic stores, bbolt
wrappers, or a `local-persistence` profile. Selecting
`profiles = ["local-persistence"]` fails with `resolve.unknown_profile` and
points here.

---

## Admission bar (when this may become a profile)

These identifiers remain recipes until **all** of the following hold:

1. **Two real Generated Projects** independently retain substantially the same
   complete local-persistence architecture (files, dependencies, docs, **and**
   tests) after real use — not synthetic fixtures alone (`REQ-247`).
2. A full **Section 19.4** profile admission checklist is completed with recorded
   evidence (see [`docs/dev/profile-admission.md`](../dev/profile-admission.md)).
3. An **accepted revision** of SPEC-FOUNDRY-002 reclassifies the candidate and
   admits a catalog profile ID.

Until then: document patterns here; add persistence **by hand** in the generated
project; do **not** reintroduce a catalog profile ID or schema fields.

## Normative bounds (Section 21.2 / REQ-075)

1. **Ordinary files first** — prefer a single versioned file (or a small set of
   explicit paths) over an embedded database.
2. **Atomic write-rename** for updates (write temp → fsync as needed → rename)
   so readers never observe partial content.
3. **Explicit schema/versioning in the file content** (header field, envelope
   version, or equivalent) — not implicit “whatever the last struct was.”
4. **Adopt `go.etcd.io/bbolt` (v1.5.0)** only for a **demonstrated transactional
   local key/value** need — not because “we might need it later.”
5. With bbolt: **domain-named buckets**, **explicit encodings**, and **tests**;
   never a generic wrapper package or a speculative metadata bucket.

## Recommended package placement

Follow generated growth rules (`docs/architecture.md` in the Generated Project).

| Concern | Suggested package | Notes |
| ------- | ----------------- | ----- |
| Path resolution / open | `internal/<feature>` or thin `internal/store` | Keep paths injectable for tests |
| File format encode/decode | Same package or `internal/<feature>/fileformat` | Version field mandatory |
| bbolt (only if needed) | Package that owns the **domain** data | No project-wide `internal/db` framework |

Side-effect boundaries (filesystem, bbolt) stay behind small interfaces or
constructor-injected handles so pure domain logic remains unit-testable.

## Pattern A — ordinary files (default)

Use when state is a document, cache blob, or small structured record set.

### Shape

```text
<data-dir>/
  state.json   # or .toml / length-prefixed binary — pick one, version it
```

### Rules of thumb

- **One writer** path in the code; readers tolerate “file missing” as empty
  state when that is valid.
- Envelope example:

  ```json
  {
    "schema_version": 1,
    "payload": { }
  }
  ```

- **Atomic replace:** write to `state.json.tmp` (same directory), then
  `os.Rename` over `state.json`. On POSIX this replaces atomically for
  readers opening by path.
- Mode: prefer **0600** when the file may contain sensitive material.
- Do not invent multi-directory hierarchies until a second real use case
  forces it.

### Illustrative fragment

```go
// Illustrative — not generated by Foundry.
package statefile

import (
	"encoding/json"
	"os"
	"path/filepath"
)

type Envelope struct {
	SchemaVersion int             `json:"schema_version"`
	Payload       json.RawMessage `json:"payload"`
}

func Save(dir, name string, env Envelope) error {
	path := filepath.Join(dir, name)
	tmp := path + ".tmp"
	b, err := json.MarshalIndent(env, "", "  ")
	if err != nil {
		return err
	}
	if err := os.WriteFile(tmp, b, 0o600); err != nil {
		return err
	}
	return os.Rename(tmp, path)
}
```

### Testing

| Case | Expectation |
| ---- | ----------- |
| Missing file | Empty/default state or typed “not found” |
| Round-trip | Save → load equals input |
| Corrupt / wrong version | Clear error; no panic |
| Partial write simulation | Rename-only publish; temp left behind is harmless |
| Concurrent writers (if relevant) | Document single-writer assumption or lock |

## Pattern B — bbolt (transactional need only)

Adopt bbolt **after** you can answer yes to:

- Multiple keys must update **atomically** in one commit, **or**
- You need a durable local KV with crash-safe transactions, **and**
- A single versioned file is measurably worse for the real access pattern.

**Pin:** `go.etcd.io/bbolt` **v1.5.0** (re-verify when adopting).

### Rules

| Rule | Detail |
| ---- | ------ |
| Domain-named buckets | e.g. `orders`, `sessions` — not `data` / `meta` / `default` |
| Explicit encodings | Document protobuf/JSON/binary; version the value envelope |
| No generic wrapper | Do not publish a reusable “BucketRepository[T]” framework in-tree |
| No speculative buckets | Create a bucket when the feature needs it, not “for later” |
| Tests | Open temp DB under `t.TempDir()`; cover commit, rollback, missing key |

### Illustrative fragment

```go
// Illustrative — only after transactional need is demonstrated.
package orderstore

import (
	"fmt"

	bolt "go.etcd.io/bbolt"
)

var bucketOrders = []byte("orders")

func PutOrder(db *bolt.DB, id string, encoded []byte) error {
	return db.Update(func(tx *bolt.Tx) error {
		b, err := tx.CreateBucketIfNotExists(bucketOrders)
		if err != nil {
			return err
		}
		if id == "" {
			return fmt.Errorf("empty order id")
		}
		return b.Put([]byte(id), encoded)
	})
}
```

### Testing

| Case | Expectation |
| ---- | ----------- |
| Put/get round-trip | Same bytes |
| Missing key | Typed miss, not panic |
| Update failure mid-tx | No partial key visible after rollback |
| Bucket name | Constant matches domain; no anonymous bucket |

## Choosing A vs B

```text
Need crash-safe multi-key transactions or heavy KV access?
  no  → ordinary files (Pattern A)
  yes → bbolt (Pattern B), with domain buckets + tests
Still unsure?
  → ship files first; measure; adopt bbolt only with evidence
```

Repetition of the **same** file or bbolt architecture across two real projects
is the evidence that feeds a future profile proposal — not a reason to smuggle
`local-persistence` into today’s catalog.

---

## Anti-patterns (do not reintroduce)

- Generated empty repositories or `// TODO persist here` scaffolding
- ORM/framework layers without a product requirement
- Global singleton DB handles and `init()` openers
- Treating persistence as a Foundry profile selection
- “Metadata” buckets for undocumented framework bookkeeping
