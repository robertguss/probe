# Configuration recipe (Section 21.1)

**Classification:** Recipe only — **not** a schema-1 catalog profile.  
**Requirements:** REQ-073, REQ-074 (SPEC-FOUNDRY-002).  
**Normative anchor:** Section 21.1 of
[`docs/02-definitive-foundry-specification-revised-fable-5.md`](../02-definitive-foundry-specification-revised-fable-5.md).

This document is **post-generation guidance** for project owners and agents.
Foundry does **not** generate configuration loaders, config schemas, example
credentials, or a `configuration` profile. Selecting `profiles = ["configuration"]`
fails with `resolve.unknown_profile` and points here.

---

## Admission bar (when this may become a profile)

These identifiers remain recipes until **all** of the following hold:

1. **Two real Generated Projects** independently retain substantially the same
   complete configuration architecture (files, dependencies, docs, **and** tests)
   after real use — not synthetic fixtures alone (`REQ-247` dogfood measurements).
2. A full **Section 19.4** profile admission checklist is completed with recorded
   evidence (see [`docs/dev/profile-admission.md`](../dev/profile-admission.md)).
3. An **accepted revision** of SPEC-FOUNDRY-002 reclassifies the candidate and
   admits a catalog profile ID.

Until then: document patterns here; add config code **by hand** in the generated
project; do **not** reintroduce a catalog profile ID or schema fields.

---

## What Foundry will not do

| Action | Status |
| ------ | ------ |
| Catalog profile ID `configuration` | **Forbidden** (REQ-073) |
| Generate config packages, TOML samples, or secret fields | **Forbidden** (REQ-074) |
| Project Spec schema fields for config paths/secrets | **Forbidden** |
| Automatic config-file discovery across the filesystem | **Out of scope** |

MVP and all phases until a revision: `profiles = []` (or only admitted profiles
such as post-MVP `distribution`).

## Normative bounds (Section 21.1 / REQ-074)

1. **Precedence:** explicit flags > environment variables > **one** optional
   TOML file (explicit path only).
2. **No automatic discovery** of config files (no walking `$HOME`, XDG, or CWD
   for “default” names).
3. **Libraries when needed** (exact pins from Stage 4 evidence; re-verify on
   adopt):
   - `github.com/caarlos0/env/v11` **v11.4.1** — typed environment decoding
   - `github.com/BurntSushi/toml` **v1.6.0** — explicit file parsing
4. **Secrets** enter **only** via environment injection (or the OS secret
   store the operator already uses). Never generate secret fields, committed
   credentials, or example tokens that look real.
5. **Permissions:** config files the tool **creates** that may hold sensitive
   values use mode **0600** (create exclusive when possible).

## Recommended package placement

Follow generated growth rules (`docs/architecture.md` in the Generated Project):
responsibility-named packages under `internal/`, no `util/` / `common/` buckets.

| Concern | Suggested package | Notes |
| ------- | ----------------- | ----- |
| Flag surface | Archetype CLI package (`internal/cli`) | Cobra flags only at the process edge |
| Typed env + optional TOML merge | `internal/config` (or a domain name if config is inseparable from one feature) | Pure decode + merge; no network I/O |
| Secret material | Never stored in TOML samples | Read from env at the boundary; pass as values/interfaces inward |

**CLI:** parse flags first; if a `--config` (or equivalent) path is set, load
that **one** file explicitly; overlay env last or per library convention while
preserving the **flags > env > file** effective precedence for operator mental
models (document the exact merge order in the project’s `docs/commands.md`).

**TUI:** avoid a startup path that **requires** a config file before the UI can
open (this was a Stage 4 contradiction that helped retire the profile). Prefer
env for process-level settings; optional explicit path after the app is running
if the product truly needs a file.

## Patterns

### 1. Flags only (start here)

Many tools need only a handful of flags. Add them in the CLI package with
stdlib/`cobra` defaults. No new dependency.

### 2. Typed environment variables

When many env vars appear, introduce `caarlos0/env` for struct tags and
validation. Keep names stable and document them in `docs/commands.md` and
`AGENTS.md` only if they are operator-facing (avoid duplicating long lists in
three places — pick one authority and link).

```go
// Illustrative fragment — not generated by Foundry.
package config

import "github.com/caarlos0/env/v11"

type Settings struct {
	LogLevel string `env:"LOG_LEVEL" envDefault:"info"`
	// Secrets: env only — never a TOML field.
	APIToken string `env:"API_TOKEN"`
}

func FromEnv() (Settings, error) {
	var s Settings
	if err := env.Parse(&s); err != nil {
		return Settings{}, err
	}
	return s, nil
}
```

### 3. One optional TOML file (explicit path)

Use when operators need a checked-in **non-secret** defaults file. The path
comes from a flag or a single env var — not from multi-path search.

```go
// Illustrative fragment — explicit path only.
package config

import (
	"os"

	"github.com/BurntSushi/toml"
)

type FileSettings struct {
	Endpoint string `toml:"endpoint"`
	// No secrets in this struct.
}

func FromTOML(path string) (FileSettings, error) {
	var s FileSettings
	if path == "" {
		return s, nil
	}
	b, err := os.ReadFile(path)
	if err != nil {
		return s, err
	}
	if err := toml.Unmarshal(b, &s); err != nil {
		return s, err
	}
	return s, nil
}
```

When the tool **writes** a config file that might later hold secrets, create it
with mode **0600** and refuse to overwrite via symlink (follow project FS
safety practices; Foundry’s own generate path uses exclusive create — mirror
that discipline if you write files).

### 4. Merge order checklist

Document and test:

1. Load file (if path provided).
2. Apply env (overrides file for overlapping keys, or document exceptions).
3. Apply flags (always win for the same setting).

Reject unknown TOML keys if you want fail-closed config (mirrors Foundry’s
own `spec.unknown_field` posture).

## Testing guidance

| Case | Expectation |
| ---- | ----------- |
| Default (no file, minimal env) | Sensible defaults; binary starts |
| Explicit config path | File values applied; missing path is a clear error |
| Env overrides file | Documented precedence holds |
| Flag overrides env | Documented precedence holds |
| Secret only in env | TOML without secret still works; empty secret fails closed if required |
| Unknown TOML key (if fail-closed) | Error names the key |
| Permissions on create | Created sensitive file is 0600 |

Put unit tests beside the package (`internal/config/config_test.go`). Prefer
table-driven cases and temp files under `t.TempDir()` — never touch the user’s
real config locations in tests.

---

## Anti-patterns (do not reintroduce)

- Scaffolding empty `Config` structs the owner must fill to compile
- Multi-file hierarchical config frameworks (Viper-style discovery)
- Committing `.env` with credentials or “example” live tokens
- Treating configuration as a Foundry profile selection
- Generic `internal/util/config` bags shared by unrelated domains
